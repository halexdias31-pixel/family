# @family. — the map

A tutoring business's site. Static front end on GitHub Pages, Google Apps Script backend, three
spreadsheets as the database. No build step, no framework, no package.json for the site itself —
`index.html` lists the JavaScript files and the browser concatenates them into one global scope.

**Read this first, then the file you need.** It exists because the codebase is 64% prose: 1.4 MB of
source, 511 KB of actual code, and the rest is comments explaining decisions that were paid for in
bugs. That prose is the most valuable thing here and it is also why finding anything takes a while.

---

## The shape of it

```
index.html      lists the js/ files IN ORDER and starts the boot fetch while still parsing
style.css       448 KB, 1970 rules. --css-version at the top says which build is running
js/             40 files, ONE SHARED GLOBAL SCOPE. No imports. Order is load-bearing.
bundle/         GENERATED by tools/bundle.js (run by build-stamp): first.js, later.js, lazy.js = js/ joined in FILES order; served instead of js/ (?dev or ?nobundle loads js/). Never edit (1211).
backend/        the Apps Script project. GitHub only holds a COPY — see "Deploying" below.
check/          the harness that replaces looking at it on a phone
```

### The one rule in `js/`

Every file shares one scope, so **a file must not be reordered against the others**. `index.html`
holds the list; the list is the order. Nothing fails at load if a name is missing — that is the cost
of plain scripts over modules, and it is paid by `js/check.js`, which reads every file and reports
any name used but never declared. Run it after every change.

### The spine

| File | What it is |
|---|---|
| `js/shell-*.js` | **The runtime**, six files cut in order from `shell.js` (1040), `shell-boot.js` first; checks read them as one via `tools/piece-src.js` (`pieceSrc('shell')`; `me-*.js`, `keypad-*.js` and `book-*.js` (book-steps, book-rows, book-spine) likewise). `screen(id, draw)` registers a screen, `go(id)` switches to one, `placeCells()` positions the panes, `toast()` speaks. 25 KB of code under 97 KB of comments. |
| `js/data.js` | `API` (the Apps Script URL), `DATA`, `load()`'s state, the small helpers, `missingKeys()`. |
| `js/boot.js` | Last file loaded. Draws the first screen, then calls `load()`. Nothing may go below it. |
| `js/find-*.js` | The funnel — the app's main surface, and the engine of both finders (`FINDERS`, `inFinder_`): sixteen files cut in order from one (1040), `find-finder.js` first, `find-measure.js` last; checks read them as one through `tools/find-src.js`. |
| `js/book-*.js` | Sessions, seats, payment: cut in order from book.js into book-steps, book-rows, book-spine. |

Nineteen screens are registered (eighteen for anybody but an admin), in `TAB_ORDER` (js/shell.js),
grouped by purpose since 21 Oct (docs/history/392), and `data/settings/columns.json` lists the same order
(`check-doors.js` fails if they part). Social: `feed` (where the app opens, `TAB_HOME`), `spotlight`,
`reel`, `dm`. Learning: `stuff` (Find, the funnel —
questions, answers, practicals, projects, bundles, the content cards, the boxers and their fights, the
Bible for an admin — and the root), `res` (**Find 2**: the same finder again, immediately right of Find,
with a state of its own; the id is `res` from the two days it held the resources), `saved` (Progress was dissolved into Student settings, 461), `tools` (left of Find since 444). Business: `booking`, `shop` (things for sale and the
basket — Find no longer has a Shop door). Then `games`. Then each account type's settings (461): `family` (Parent settings),
`staff` (Tutor settings), `account` (Student settings, where you sign in and out); then the profiles, a card each:
`tutors` (Tutor profiles), `students` (Student profiles, Needs help on top for Staff), `parents` (Parent profiles); and last,
**for an admin only**, `biz` — the business records (insurance, tax, legal and data, safeguarding, money and company). A tab
marked `admin: true` is left out of `TABS` for anybody else by `columnsFor_` in shell.js, which also
makes its `<section>` for an admin and takes it away again — so it has none in index.html, and signing
in or out adds or removes it without a reload.

**One finder, twice** (docs/history/329, 347). `stuff` and `res` carry the **same list** and ask the
same funnel — *"an identical second finder"*, so a student can keep a content card up in one while answering
questions in the other — and what makes them two is their **state**: words, chips, page and kept place
(`find:place`, `res:place`). One funnel bound to two states: `inFinder_(F, fn)` in find.js parks one
finder's `STUFF` and memos and puts the other's in their place, so the engine reads `STUFF` as it always
did. **Outside a binding `STUFF` is Find's** — every other file and every check that writes it means
Find. A timer, microtask, promise or `afterSlide_` job runs outside the binding and must capture its
finder and bind again; anything that forgets "the found list" forgets every finder's
(`finderForgetFound_`). Find's front pages (the booking form, posts, bundles) and the Tools tail of the
fill stay Find's alone. A kept card Saved cannot draw whole has `Open · in Find`. The 10–12 Oct split
(Find without the resources, the second column with only them) is gone; don't bring back a membership
rule per finder.

### The admin's layout has no undo (477)

An admin's tiles on a widget or card move it or delete it, for everybody, saved at once (`layoutSave`,
config's `layout` row). There is no Layout card, no Add back and no Reset: the current layout IS the
layout. Delete asks twice in place and is final; `deleted` only keeps the item from being drawn again.
A widget or card added in code later still appears in its own column. `layoutSave` refuses an empty layout.

### Layout, and why the checks are shaped the way they are

Screens sit **side by side** and slide — `placeCells()` positions them with transforms. So at any
moment most of the app is parked off-canvas left and right of the viewport. **That is the design,
not a bug.** Any check that asks "is this element past the right edge of the window" will report
about 156 false alarms. Ask "does this box scroll sideways when it was not told it could" instead.

## Where the data comes from

`DATA` is one JSON payload from one `doGet`. The sheet is the database; the site reads it and
almost never writes to it directly.

- **`brand` tab** — key/value. Read as `brand('key', fallback)`. Every call passes a fallback, so an
  empty tab still renders. **This is the pattern to copy for anything new.**
- **`config` tab** — key/value numbers and switches, reaching the site as `DATA.constants.vars`.
- **`facets` / `kinds` tabs** — what the funnel asks and what the answers are called. These moved out
  of `find.js` deliberately: editorial, changes often, changing it should not be a deploy.
- **The library is two halves** (docs/history/397, docs/library.md). The four library files in `data/` are the
  cards — every column the funnel asks, sorts, counts and tags by — plus `lib_has` (the private fields the Ledger
  holds for the row) and a question's `function_verified`. The words, answers, figures and method text are rows
  of `lib_questions`, `lib_content`, `lib_practicals` and `lib_projects` in the Ledger (`LIB_FILES` in
  constants.gs), copied once by `library-to-ledger` and fetched a card at a time by `libItems` (signed in,
  `library_items_per_day`). A card whose words have not come is one waiting page (`libWaitHtml_`). The teaching
  animation rows stay public whole. Tools: `tools/lib-private.js`; checks: `check/lib-full.js`.
- **What must exist is the specification** (1213, 1214): `data/spec/<board>-<code>.json` is every spec (the `measured` ones count);
  `node tools/coverage.js -v` maps lessons (`spec_ref`), questions and figures onto the points, writes each point's `links`
  back, `data/specs.json` (Find's Library › subject › Specification card) and `data/coverage-health.json` for *Library content*.
- **There are no textbooks on screen: each chapter row of `data/textbooks.json` is a CONTENT CARD**
  (kind `content`, `What kind · Content`; docs/history/347, part 2). *"Forget the whole concept of it
  being a text book. It's just a "content card""* — the owner, 12 Oct. A card wears the question
  library's tags — Subject, Level, Tier, Topic, a board only where its content is one board's — and
  its topics are spelled EXACTLY as data/questions.json or data/topics.json spells them
  (`check-textbooks.js`); every maths card has at least one. The cover row (`chapter: 0`) is only the
  defaults its chapters inherit; a chapter's own cell wins. **The file keeps its name, its row shape
  and `DATA.textbooks`**, because `tools/anim_row.py`, `splashSync_` and `check-anims.js` are written
  against them; internal `tb*` names stay too. Nothing a person sees says textbook, book or chapter.
- **The teaching animations are rows of `data/textbooks.json`** — Pythagoras, the sieve, Bayes, the
  solar system, how many 3s fit into 4 and 24 more, each directly under the chapter row it teaches (`anim`, `title`, `about`,
  `html`, `css`). Its content card plays it on a page of its own, in whichever finder it is opened; the loading screen draws a copy the
  device kept from the last load (`splashSync_` in shell.js, read by the picker in index.html — one
  load behind). *"The source for the animations should be in text books"* — the owner, 8 Oct.
  **Each one has ONE source, and which it is depends on the drawing.** Fourteen are written by a
  script — `area bayes cent coin fib fit gal index mxc orbit pyth sieve sine venn` (`gal` is
  `tools/galton.py`, `orbit` is `tools/solar.py`, the rest `tools/<id>.py`, all through
  `tools/anim_row.py`): for those **the script is the source** — change it and re-run it, and never
  edit the row by hand, because the next run puts back everything the script writes and nothing
  notices but `check-anims.js`. For the other 15 **the row is the source**: edit it in place. Never
  in `index.html` or `style.css`: the loading screen there has no drawing of its own — the 13
  splashes that taught nothing were deleted on 10 Oct (*"delete all animations for loading which dont
  come from text books or arnt educational"*). With nothing kept (a first visit), the splash is the
  name, still, with `loading_()`'s loader under it, written out by hand; `check-loading.js` holds
  that copy to `loading_()` byte for byte, `check-css.js` keeps an inline splash out (what `#splash`
  holds is a closed list), and `check-anims.js` fails on a teaching one left there. See
  docs/history/304, 322.
- **Every paper has a health score** — `paperHealth_` in js/library.js, the share of its points that pass; the finder shows `Ready · 99%` and a Health tile (that paper score was deleted, 388; the site score is the Optimiser, `tools/health.js`) to everybody (*"No, everyone can see the scores"*), and `check-health.js` prints them all. See docs/history/354.
- **Every drawing in `data/questions.json` (`diagram`) has a PNG twin** in `data/diagrams/<first 12 hex of
  the SHA-256 of the drawing>.png`, for the Sunday email (Gmail shows no SVG; *"No jpgs"* — linked in the
  body, never attached). **Written by `tools/diagram_png.js`** (the site's CSS, paper palette, 2x) — re-run
  it after changing any drawing, never draw one by hand; `check-diagram-png.js` fails on a drawing with no
  twin, a twin with no drawing, and a backend that names one differently. See docs/history/351.
- Everything else — people, venues, jobs, pricing, posts, links, laws, landmarks, holidays — is a
  tab, listed in `TAB` in `backend/constants.gs` with the column list in `SCHEMA` beside it and the
  file it lives in in `WHERE`. **All three have to name it.** `TAB` without `WHERE` is a tab nothing
  can open; `WHERE` without `SCHEMA` is a tab `ensureSchema` will never repair. `check-tabs.js` is
  the instrument, and it runs before `check-columns.js` because a tab nobody can open has no
  columns.

**A key the site asks for and the backend does not send fails silently.** `|| []` turns it into an
empty list, which looks exactly like an empty database.

`node js/check-payload.js` is the instrument for this. It reads the files, so it sees every read
whether or not anybody performed it — which is the difference between it and `missingKeys()`, the
console helper that only records keys something actually reached for, and so only knows about the
screens you happened to open, in the state you happened to be in, as the person you happened to be
signed in as. A key read only by an admin on the print queue is invisible to `missingKeys()` until
an admin opens the print queue.

It reports two directions and they are not the same severity. **Read and never sent** is a feature
that silently does nothing, and fails the build. **Sent and never read** is a tab walked and shipped
to every phone on every load for nobody — weight worth deleting, but it breaks nothing, so it
reports and does not fail. There are 23 of those right now.

Keys that are read, deliberately not sent, and known about live in `ACCEPTED` at the top of that
file, **one written reason each**. They are still printed. The point of the list is that a *new*
dead key fails loudly instead of joining a red that nobody reads.

### CI, quick mode and the live smoke test (780)

- `.github/workflows/checks.yml`, every push and every PR to main, core only (99, 9 Nov), 9 jobs in parallel: `fast` (`check.js` +
  `check-all.js --fast`) and `flow k/8` (`FLOW_PART=k/8 node --max-old-space-size=3000 js/check-flow.js`, core journeys), and on a
  PR the `stability guard` (`js/check-stability.js --base .base`). About 10 minutes of wall time. `.github/workflows/nightly.yml`
  (02:41 UTC and by hand, report-only) runs the rest: secondary checks and journeys, `browser k/8` (`check-all.js --slow=k/8`)
  and `heavy k/6`.
- **CI has no private words.** It sets `LIB_PRIVATE=absent`: check/lib-full.js then never seeds data-private/ from history,
  and every read of the words throws `LIB_ABSENT`. A check that needs them whole calls `needWords()` (prints "skipped 1
  library check", exits 0); check-flow skips and counts each such journey (`skipParts`); a read a check swallowed is still
  said at exit. Every skip goes to `$LIB_SKIP_LOG` and each job's summary lists it. Skipped is not green: those still need
  `npm run check` on a machine with the words. Locally nothing changes.
- `npm run check:changed` (`js/check-changed.js`): only the checks a change affects (against origin/main, plus uncommitted
  files), from its glob map; a file it does not know runs everything. `--list` prints, `--base=REF`.
- `.github/workflows/live.yml`, nightly, by hand and 30 minutes after a push to main: `check/live-smoke.js` loads
  https://atfamily.co.uk/ signed out at 390 and 1440 px, visits every column in `TABS`, fails on a console error, page error or
  failed same-origin request, and on a live `--css-version` that is not main's. Screenshots are an artifact.

## House style

Follow it. It is unusual and it is deliberate.

- **Comments say WHY, and what went wrong before.** Not what the line does. Most of them are a bug
  report written from the far side. Match the density of the file you are in.
- **Fallbacks everywhere.** `brand(k, or)`, `|| []`, `try/catch` around anything that can be absent.
  An empty or broken sheet must still produce a working site.
- Plain scripts, no modules, no framework, no build.
- **A THING has tiles; a FORM has buttons.** This is the rule that decides which of the app's two
  action surfaces to use, and it was never written down — which is the only reason the app looked
  inconsistent. Measured: 46 inline `<button>`s against 21 `tile_()` calls, so tiles are the
  *minority*, and the split is by context rather than by accident.
  - **Tiles** (`tiles.js`, one renderer) are the action row under a **thing**: a paper, a tutor, a
    shop item, a session. One `tile_({icon, label, note, act, data})` per action, wrapped in a
    `.tile-row`. Tap targets, icons and the press animation come from one place, and `check-doors`
    pairs every `act` against a handler.
  - **Buttons** are the controls inside a **form or a dialog** — the booking form, the pay sheet,
    the composer. A form's buttons belong to the form.
  - **On a question's pages, everything is a tile** — the owner, 5 Oct: *"check button should be a
    tile"*, *"lock should be a tile too. same as undo and clear. it should all be tiles."* So Check,
    Show/Hide the answer, the pen's lock/undo/clear and its ruler/compass, and Mark with AI are tiles
    even though they act like a form's controls. The two exceptions are the answer itself — the
    keypad's keys and the multiple-choice options — because those are what is being written, not
    actions on it. When in doubt elsewhere, the owner's lean is the same: tile.
  - **Tiles win any tie.** One renderer means one place to fix a tap target; 46 inline buttons is 46
    places to get it wrong. If you are unsure which you are building, it is a thing, and it is tiles.
  - A tile has room for a label and about three words of `note`. When an action needs a real warning
    — "everyone is withdrawn", "never as though Stripe had confirmed it" — put **one** paragraph
    under the row rather than one per button. See `jobAdminOpts_`.
- **THERE ARE TWO PALETTES.** The screen is black and gold (`--bg`, `--gold`, `--ink`, `--line`).
  Everything standing in for PAPER — the receipt, the job stubs, the roster, the print sheet, the
  calendar, the splash — is cream and warm ink (`--paper`, `--paper-ink`, `--paper-dim`,
  `--paper-faint`, `--paper-strip`, `--paper-rule`). Only the first was ever tokenised: the paper
  one was six hex codes written out by hand, `#f4f1e8` alone in 29 rule-groups, so "make the paper
  warmer" was a find-and-replace across ~70 declarations and one missed leaves a card with two
  different papers in it. **Never write a paper colour as a literal.**
- **Which palette a colour belongs to decides its scope.** A colour used by more than one component
  is a `:root` token. A colour that belongs to ONE component — a chess board's cream and charcoal,
  which is that board's own convention and not this app's — is defined on that component
  (`.chess { --chess-light: … }`) so it is named without being offered to the whole stylesheet.
- **Tap targets in `px`, everything else in `rem`.** Line 121 sets the root to
  `clamp(13.5px, 3.8vw, 16px)`, so a rem is 14.82px on a 390px phone. `2.75rem` for a 44px target
  comes out at 40.75px and still fails. A fingertip is the same size on every screen; it is the one
  measurement here that must not scale.
- **A WAIT IS `loading_()`, AND NOTHING ELSE.** Three gold dots, from one function in shell.js and one
  block in style.css — in place of what is coming, a whole page on its own, or over markup already
  drawn (`aria-busy="true"`, taken off by `loaded_`). The owner, 9 Oct: *"Every widget has unique
  loading look. They should all have a simplistic simple loading thing."* No waiting sentence, no
  skeleton, no spinner of a card's own; an error or an empty result keeps its words, and a press
  already sent keeps `send_`'s ring. **Whether the payload is still coming is `awaiting_()`, never
  `!LOADED`** — `LOADED` is true once a failed first load has finished, while the quiet retry is
  still asking. `check-loading.js` fails on a waiting phrase, and on any drawn text that trails off in
  "…", unless it is listed with a reason. See docs/history/306.
- **EVERY BOX TYPES ON THE @family KEYPAD.** The owner: *"make it so the keyboard is the @family
  keyboard everywhere."* `kpBind_` (js/keypad.js) binds every `<input>`, `<textarea>` and editable piece
  as it is drawn: `inputmode="none"` and its face (`data-kpb`) read from the markup — a number, tel or
  `inputmode="numeric|decimal|tel"` opens on the digits, an email or url on the letters with @ . /,
  anything else on the letters. So write the box's real `type`, `inputmode`, `autocomplete` and
  `autocapitalize` and nothing else: never `inputmode="none"` or `data-kpb` by hand, never `readonly` to
  keep a keyboard away. Selects, pickers, files and ticks are left alone. `check-keyboard.js`. See
  docs/history/528.
- Version constants — `BACKEND_VERSION`, `DOGET_VERSION`, `DOPOST_VERSION`, `BOOKING_VERSION` — are
  compared on the **whole stamp**, so bump all four together or the You screen reports the untouched
  ones as "Not deployed".


## Notes for Claude

When the owner says "read my notes", open the Drive file "Notes for Claude" (plain text, in the `family-library-imports`
folder; or the Ledger tab `claude_notes`) and work through the open ones. Each block is
`[note_id] column › item_label (item_id) — date` then the note; `item_id` is the widget's or card's layout id. A note made
on Find or Find 2 carries its funnel `Path:`; one with a picture carries a `Picture:` Drive link. See docs/history/484.

**Files from the owner (515)** are in the Drive folder "Claude inbox" (beside "Notes for Claude", in `family-library-imports`),
one subfolder per batch with the chosen folder's paths kept; the note carries a `Files: Claude inbox/<batch> (N files) — <link>` line
and the first names. A session incorporates them **only when the owner asks** — never on its own because they are there.

**Marking one done is Claude's job (498).** A session that addresses a note appends its `note_id` to `data/notes-done.json`
(a JSON array of ids only — never the note's words: the repo is public) and commits it with the fix. On the admin's next
open (`setupOnAdminLoad_` → `claudeNotesDoneSync_`, at most every ten minutes) the backend marks those ids done in
`claude_notes` and rewrites the Drive file. Idempotent. The site has no Done tile and lists no notes any more.

## History

The full record of past bugs and decisions (about 1.2 MB) lives in `docs/history/`, one file per topic, listed in `docs/history/README.md`. It is NOT loaded automatically. Before changing an area, `grep -ril <keyword> docs/history` and read the matching file: those notes record why the code is shaped the way it is and what was tried and reverted.

Recurring lessons, in one line each: fix the rule, not the instance; a fixture must send what `doGet` really sends; a screenshot is the last word on anything drawn; print a count rather than a silence; a mutation proves a check only when the real files go green again.

# @family. — the map

A tutoring business's site. Static front end on GitHub Pages, Google Apps Script backend, three
spreadsheets as the database. No build step, no framework — `index.html` lists the JavaScript files and
the browser concatenates them into one global scope. This file is loaded into every session, so it holds
the rules only; the reasons and figures behind them are in `docs/map-detail.md` and `docs/history/`.

## Reading this repo cheaply

- Grep first, then Read a line range. Never Read a whole big file (`js/find.js`, `style.css`); a journey lives in `check/flow/NN-<feature>.js` — a new one goes in its feature's file, or a new NN file.
- Never Read or `cat` `data/*.json` whole: a `node -e`/python one-liner for the rows you need.
- A pathless Grep skips `docs/` and `data/` (`.ignore`). In `docs/history`, `grep -n` the keyword and read around the hits; some notes are 140 KB.
- Checks print one line when green; `-v` (or `VERBOSE=1`) for the detail. A failure prints every failure and why.
- A comment ending `§` was shortened: its whole story is in `docs/notes/<path>.md` (`grep -rn '<headline>' docs/notes`).
- In a workflow: maps and mechanical stages at low effort, two agents at a time, one review lens unless the change is risky.

## The shape of it

```
index.html   lists the js/ files IN ORDER and starts the boot fetch while still parsing
style.css    --css-version at the top says which build is running
js/          ONE SHARED GLOBAL SCOPE. No imports. Order is load-bearing.
backend/     the Apps Script project. GitHub holds a COPY — see Deploying.
check/       the browser checks
```

**The one rule in `js/`:** every file shares one scope, so a file must not be reordered against the
others; `index.html`'s list is the order. Nothing fails at load if a name is missing — `node js/check.js`
reports any name used but never declared. **Run it after every change.**

| File | What it is |
|---|---|
| `js/shell-*.js` | The runtime (cut from shell.js, 1040): `screen(id, draw)`, `go(id)`, `placeCells()`, `toast()`, `TAB_ORDER`. |
| `js/data.js` | `API` (the Apps Script URL), `DATA`, `load()`'s state, small helpers, `missingKeys()`. |
| `js/boot.js` | Last file loaded. Draws the first screen, then calls `load()`. Nothing may go below it. |
| `js/find.js` | The funnel — the main surface — and the engine of both finders (`FINDERS`, `inFinder_`). |
| `js/book-*.js` | Sessions, seats, payment: cut in order from book.js into book-steps, book-rows, book-spine. |

Screens, in `TAB_ORDER` (392, 461, 730, 790): `spotlight feed reel dm | stuff res saved | booking shop |
web tutors students parents apprentices | staff site account family apprentice biz`; `data/settings/columns.json` must list the same order
and mark the same card columns (`cards`, read into `CARD_COLS`; backend's copy in constants.gs is written by `tools/columns_gs.js`) (`check-doors`); an admin's layout (config `layout`, js/layout.js, 462-463, 710, 730) is laid over this default, its `order` over TAB_ORDER. `feed` is where the app opens (`TAB_HOME`). `stuff` is Find, whose cards include every tool and game (kinds `tool`, `game`; which ones is data/settings/widgets-in-find.json, 790); `res` is Find 2; the five profiles are Web, Tutor, Student, Parent and Apprentice profile; the six settings Tutor (`staff`), Web (`site`), Kids (`account`), Parent (`family`), Apprentice and Biz (`biz`) settings; every setting has one home. `biz` and `site` are admin-only — a tab marked
`admin: true` is left out of `TABS` by `columnsFor_` (shell.js), which also makes and removes its `<section>`.

**One finder, twice** (docs/history/329, 347). `stuff` and `res` carry the same list and ask the same
funnel; what makes them two is their state (words, chips, page, `find:place`/`res:place`).
`inFinder_(F, fn)` binds one finder's `STUFF` and memos. **Outside a binding `STUFF` is Find's.** A
timer, microtask, promise or `afterSlide_` job runs outside the binding and must capture its finder and
bind again; forgetting "the found list" forgets every finder's (`finderForgetFound_`). Find's front pages
and the Tools tail stay Find's alone. Don't bring back a membership rule per finder.

**Layout:** screens sit side by side and slide (`placeCells()` uses transforms), so most of the app is
parked off-canvas at any moment. That is the design. A check must ask "does this box scroll sideways
when it was not told it could", never "is this past the right edge".

## Where the data comes from

`DATA` is one JSON payload from one `doGet`. The sheet is the database; the site almost never writes to it.

- **`brand` tab** — key/value, read as `brand('key', fallback)`. Every call passes a fallback so an empty
  tab still renders. **The pattern to copy for anything new.**
- **`config` tab** — numbers and switches, reaching the site as `DATA.constants.vars`.
- **`facets` / `kinds` tabs** — what the funnel asks and what answers are called; editorial, so not in code.
- **One rule for every facet** (396): a facet is a field, a label and its readers (`FACET_KEYS`) — asked by `facetWhy_`,
  sorted by `answerCmp_`, said by `facetSay_`, coloured by `TAG_OF`, and a tag on every card. Never a per-facet flag (check-funnel).
- **Every other tab** is listed in `TAB`, `SCHEMA` and `WHERE` in `backend/constants.gs`. **All three must
  name it** (`check-tabs.js`, which runs before `check-columns.js`).
- **The library is two halves** (397): `data/questions|textbooks|practicals|projects.json` are the CARDS (ids, facet
  columns, `lib_has`, `function_verified`); words, answers and figures are in the Ledger (`LIB_FILES`, `lib_*` tabs)
  and reach a phone by `libItems` when a card opens. Never commit a private field to `data/` (`check-secrets`); a
  row-writing tool runs between `node tools/lib-private.js join` and `split`; checks read the whole library through
  `check/lib-full.js`; a new card whose words await import carries `lib_pending` (411). See docs/library.md.
- **Content cards:** each chapter row of `data/textbooks.json` is a content card (kind `content`); nothing a
  person sees says textbook, book or chapter. The file name, row shape, `DATA.textbooks` and `tb*` names
  stay. Topics are spelled exactly as `data/questions.json`/`data/topics.json` spell them (`check-textbooks.js`). See 347.
- **Teaching animations are rows of `data/textbooks.json`**, one source each (172; 436 lists them by subject).
  Script-written, all through `tools/anim_row.py` — change the script and re-run it, never hand-edit the row:
  - `area bayes bus cent coin fadd fdp fib fit gal index line lmul mean mxc neg orbit peri prot pv pyth ratio sieve sine trans venn`
    (`tools/<id>.py`; `gal` is `galton.py`, `orbit` is `solar.py`; the KS2 ones 409, on the KS2 book since 436)
  - GCSE Maths `gbal gcf gcomp genl gexp gfac gquad grot grule gsemi gsim gsimi gsoh gsurd gtree gvec` (`tools/g_<topic>.py`, 410)
  - A-level Maths `abinom achain aexp afirst ageom ahyp aincline amoment anormal aparam apascal aproj apulley ariemann aroot2 aunit avec3` (`tools/a_<name>.py`, 411)
  - Physics `phcirc phdrop phem phfiss phforce phhalf phheat phiv phmom phmotor phrefr phsank phstate phvt phwave` (`tools/ph_<topic>.py`, 419)
  - Chemistry and Biology `atom balance carbon cell covalent dna electro enzyme equil frac groups heart ionic mitosis moles natsel osmosis photo punnett rates reflex titrate` (`tools/cb_<id>.py` with `tools/cb_kit.py`, 420)
  - Computer Science `bin bubble fde gates hex insert merge packet pixel rle search stack` (`tools/cs_<id>.py`, 424; a new one makes its row with `--init`)
  - Geography `ggcoast ggcontour ggdtm gggreen gggrid ggmeander ggplate ggquake ggstorm ggwater` (`tools/gg_<topic>.py`, 423)
  - History `hbal hcur hexp hinf hmed hnop hweb hweim hww2` (`tools/h_<topic>.py`, 417)
  - English `eapos earc eforest emetre epeel escrooge esent ezoom` (`tools/e_<topic>.py`, 416)
  - Psychology and Sociology `asch ivdv lens milg msm piag samp syn` (`tools/ps_<topic>.py`, names in `anim_row.py`; 426)
  - Economics and Business `ecbreakeven eccashflow ecextern ecflow ecfx ecped ecppf ecrates ecsupply` (`tools/ec_<topic>.py`, 425)
  - Spanish and French `labuild laconj laetre lagend latime` (`tools/la_<name>.py`, 427)
  - Philosophy and RS `pcause pcave pdoubt pfall psyll ptrolley pwatch` (`tools/p_<name>.py`, 418)

  For the rest the row is the source. Never in `index.html` or `style.css`; drawn only when a chapter opens — the splash is gone (466). `check-anims.js`, `check-loading.js`. A new one is a
  script on `anim_row.Loop` that writes its whole row (`whole=True, place=…`), its class prefix unused by any other
  drawing. One drawing per thing on a chapter. See 304, 322, 409, 436.
- **Verified tags:** every question carries two ordinary funnel tags, `Accuracy verified/unverified` (row `verified: "True"` = answer checked against the official scheme) and `Function verified/unverified` (qtypes.js protocol complete and machine-marked); `verifyTags_`, find.js; `check-qtypes.js`. See 388.
- **Ranks** (400): one per account, Student < Client < Staff < Admin, read from `people.role` by `rankOf`/`rank_()` — gate on `rankAtLeast_`, never a new role check; Staff only by an approved application; family links stay on `family`. See docs/accounts.md.
- **Diagram PNG twins:** every `diagram` (the whole library, `check/lib-full.js`) has `data/diagrams/<12 hex of SHA-256>.png`
  for the Sunday email, written by `tools/diagram_png.js` — re-run it after changing a drawing, never draw
  one by hand; `check-diagram-png.js`. See 351.

**A key the site reads and the backend does not send fails silently** (`|| []` looks like an empty
database). `node js/check-payload.js` reads the files, so it sees every read: **read-and-never-sent fails
the build; sent-and-never-read only reports** (weight to delete). Known exceptions live in its `ACCEPTED`
list, one written reason each. (`missingKeys()` only knows the screens you happened to open.)

## Deploying

| What changed | How it goes live |
|---|---|
| `index.html`, `js/`, `style.css` | `git push` → GitHub Pages, about a minute. |
| `backend/*.gs` | merge to `main`; in Apps Script press ↓ (GitHub Assistant), Deploy → New version, then open the site once as an admin — setup runs itself (361). |
| Spreadsheet contents | Immediately, if the edit watch is installed. |

Every sync route replaces the project's files wholesale: code typed only into the Apps Script editor is
lost at the next sync.

**Keep-awake (rule 8.4):** the admin-load setup books one `keepWarm` trigger (every 5 minutes, never twice,
`keepWarmKeepBooked_` in `core.gs`); it GETs the app's own URL with `?ping=1`, which `doGet` answers before any
sheet work. The page never asks for the ping. `node js/check-keepwarm.js` proves both.

The routes, the two API switches and why `pullFromGitHub` is blocked: `docs/deploying.md`.

## Checking your work

`.claude/session-start.sh` runs the suite on arrival and prints `all N checks pass` or `CHECKS ARE RED
ON ARRIVAL`. A check that cannot reach its subject must exit non-zero, and a mutation proves a check
only when the real files are green again.

```bash
node js/check.js                  # names used but never declared. Run after every change.
npm run check                     # the core checks (js/check-all.js); --all adds secondary; -v per check. Before pushing.
FLOW_PART=1/4 node js/check-flow.js   # the journeys through the real app, in four parts
node check/ui.js --screen=tools   # one screen of the layout check; --shots writes PNGs
node tools/gallery.js             # one of every card and screen (pupil/parent/tutor/admin, 390 and 820) vs the approved set; report.md + side-by-sides
node tools/gallery.js --approve   # the shots just taken become the approved set (default dir: $GALLERY_DIR or <tmp>/family-gallery, never the repo)
node check/live.js --sheets s.json --out /tmp/p.json && node check/ui.js --payload=/tmp/p.json
node check/digest-dry.js --sheets s.json --week 2026-10-18 --out /tmp/sunday   # Sunday's emails, nothing sent
```

**Two tiers** (860): only Find must never break. `data/settings/tiers.json` marks each screen, widget, kind, file and check
core or secondary; core checks and journeys block, secondary ones (`--all`, `FLOW_TIER=all`) only print WARN.
Each check's header says what it proves, its flags and its port variable. The full list: `docs/map-detail.md`.

**CI** (780): `.github/workflows/checks.yml` runs the core suite on every push and PR to main in 9 parallel jobs (~10 min; the rest nightly in `nightly.yml`), with
`LIB_PRIVATE=absent` — no private words there, so the checks that need them skip, counted in each job's summary (skipped is
not green). `npm run check:changed` runs only what a change touches. `live.yml` smoke-tests the live site nightly.

## House style

- **Comments say WHY, in a line or two** (≤ 240 characters; `check-comments` enforces). The story — what
  broke, what was tried, the owner's words — goes in `docs/history/NNN`. A comment ending `§` was
  shortened and its full text is in `docs/notes/<path>.md`; `node tools/comments.js` does the move.
- **Fallbacks everywhere:** `brand(k, or)`, `|| []`, `try/catch` around anything that can be absent. An
  empty or broken sheet must still produce a working site.
- Plain scripts, no modules, no framework, no build.
- **A THING has tiles; a FORM has buttons.** Tiles (`tile_({icon, label, note, act, data})` in a
  `.tile-row`, tiles.js) are the action row under a thing — a paper, a tutor, a shop item, a session.
  Buttons are the controls inside a form or dialog. On a question's pages everything is a tile (Check,
  Show answer, the pen's tools, Mark with AI) except the keypad keys and multiple-choice options. Tiles
  win any tie. A real warning is one paragraph under the row, not one per tile (`jobAdminOpts_`).
  `check-doors` pairs every `act` with a handler.
- **One line per thing:** a form is label/value rows, one thing each; never several controls boxed in a grid (421).
- **Two palettes.** The screen is black and white (466; the accent token is still named `--gold`) (`--bg`, `--gold`, `--ink`, `--line`). Anything standing in
  for paper (receipt, stubs, roster, print sheet, calendar, splash) is `--paper`, `--paper-ink`,
  `--paper-dim`, `--paper-faint`, `--paper-strip`, `--paper-rule`. **Never write a paper colour as a literal.**
  A colour used by more than one component is a `:root` token; one component's own colour is defined on
  that component (`.chess { --chess-light: … }`).
- **Tap targets in `px`, everything else in `rem`** — the root font size scales with the viewport, a fingertip does not.
- **A wait is `loading_()`, and nothing else** — three gold dots from shell.js (`aria-busy="true"` over drawn
  markup, removed by `loaded_`). No waiting sentence, skeleton or own spinner; an error or empty result
  keeps its words. **Whether the payload is still coming is `awaiting_()`, never `!LOADED`.** `check-loading.js`. See 306.
- **Version stamps** `BACKEND_VERSION`, `DOGET_VERSION`, `DOPOST_VERSION`, `BOOKING_VERSION` are compared
  whole: bump all four together or the You screen reports the others "Not deployed".
- **Public repo:** no real names, emails or learner data in any file (`check-secrets`, `check-surnames`
  enforce part of it), and no Claude model ids anywhere.

## History

The record of past bugs and decisions is `docs/history/`, one file per topic. Before changing an area,
`grep -ril <keyword> docs/history` and read around the hits in the matching file — don't read the
README index whole.

Recurring lessons: fix the rule, not the instance; a fixture must send what `doGet` really sends; a
screenshot is the last word on anything drawn; print a count rather than a silence; a mutation proves a
check only when the real files go green again.
